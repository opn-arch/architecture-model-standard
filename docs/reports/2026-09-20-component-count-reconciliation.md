# Component Count Reconciliation

**Date:** 2026-09-20
**Commit:** `2cb4f6e` (feat/phase-5-fanout-provenance-family5)
**Scope:** G6 of the commissioning plan
  (docs/plans/2026-09-20-g1-pipelines-v3-fragment-design.md and

## Problem

Six different sources of truth report six different component counts
for the AMS self-model. This blocks any commissioning claim ("N
components in production") because the number depends on which
artifact you read.

## Evidence

| Source | Count | Notes |
|--------|-------|-------|

| `.architecture-model.v3.yaml` (pipeline_v3 output, pre-fragment) | **26** | AST-derived by pipeline_v3 clustering; different granularity than 2.x hand-curation. |
| **Merged v3 model (pipeline + fragments)** | **27** | Adds 1 authored component from `.architecture/model/*.v3.yaml` fragments (COMP-VIEWER from `viewer.v3.yaml`). |
| `CONTEXT.md` auto-managed footer | **29** | Written by `opencode-arch` `architect_scan` at some past time; stale. |
| `CONTEXT.md` narrative "Model Metrics" table | **16** | Cluster-of-clusters summary rolled up by module; not a raw component count. |
| `.architecture/CONTEXT.md` (opencode-arch capabilities view) | **22** | 20 COMP-3-* + 2 COMP-4-* from `architect_scan` (this session's system-reminder). |
| Session's own R7/R8 report (§5) | **25** | Snapshot before this session's fragment landing; historical. |

## Root cause

There isn't one "component count" — there are **five distinct
questions**, each answered by a different artifact:

1. **"What's in the current v3 substrate?"** → 27 (merged v3 model at
   HEAD `2cb4f6e`). This is the number for commissioning claims about
   what v3 tooling (viewer, walks, validator) sees.
2. **"What does pipeline_v3 auto-extract?"** → 26 (raw pipeline
   output). Deterministic, AST-derived, floor for what v3 sees.
3. **"What did the pre-v3 hand-curated 2.x model claim?"** → 34.
   Historical. Legacy 2.x model is deprecated (see `parser.py`
   DeprecationWarning). Superseded by v3.
4. **"What does OCA `architect_scan` see today?"** → 22, expressed
   as a coarser grouping (COMP-3-* by import affinity). Different
   granularity than pipeline_v3.
5. **"What did older docs claim?"** → 16, 25, 29 — all stale.

## Canonical choice

**Adopt count = 27 (merged v3 model at HEAD).**

Rationale:

* v3 is the destination substrate; 2.x is deprecated.
* The merged v3 model is what every v3 tool actually consumes
  (viewer, walks, validator, slicer). It's the source of every
  operational metric this session generated.
* Both 26 (pipeline-only) and 27 (merged) are traceable, deterministic
  numbers. Using the merged figure means new authored components in
  fragments count — which is correct (COMP-VIEWER is a real
  architectural component even though the pipeline can't extract it
  from viewer code that lives in `scripts/`).

Corollary: any commissioning claim ("AMS ships with N components")
should cite **27 as of `.architecture-model.v3.yaml` + fragments in
`.architecture/model/*.v3.yaml`, HEAD `2cb4f6e`**.

## Residual divergence (intentional)

Three stale numbers remain and will keep re-diverging on their own
schedules — deliberately not "fixed":

1. **`.architecture-model.yaml` (34)** — legacy 2.x, deprecated. Will
   remain until deprecation window closes. Do not update.
2. **`CONTEXT.md` auto-managed footer (29)** — regenerated by OCA
   `architect_scan` on demand. Will fluctuate every scan.
3. **`.architecture/CONTEXT.md` (22)** — regenerated by OCA
   `architect_scan` on demand. Same as above.

These self-heal on the next `architect_scan` invocation. No manual
edit warranted.

## Not a bug, filed as G6.1 for future consideration

`pipeline_v3` outputs 26; merged model has 27. The +1 (COMP-VIEWER) is
authored because the viewer sits in `scripts/` which pipeline_v3
doesn't scan by default. Two ways to close this:

* **G6.1a**: teach pipeline_v3 to include `scripts/` in its scan.
  Deterministic, but may add noise from one-off scripts.
* **G6.1b**: leave as-is. Authored fragments are the right place for
  entities the pipeline can't auto-extract (this is why fragments
  exist).

Recommend **G6.1b** — authored fragments are the escape hatch for
exactly this case, and forcing all components to be AST-derivable
would be a regression against MBSE flexibility.
