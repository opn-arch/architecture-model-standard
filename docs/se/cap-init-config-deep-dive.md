# Config YAML Generation & Self-Bootstrapping — Deep Dive

## Modularity Principles

Every function in the config discovery pipeline should:

1. **Return typed results** — `ProjectConfig`, `DiscoveryReport`, not raw dicts or implicit side effects
2. **Log what was evaluated** — every heuristic checked, every candidate accepted/rejected, with reasons
3. **Track success metrics** — files discovered vs claimed, blocks with docstrings vs without, layout detection confidence
4. **Define improvement criteria** — coverage of `_`-prefixed dirs, `pyproject.toml` awareness, monorepo support
5. **Accept extensibility** — domain profiles extend the config schema for non-software systems (controls, mechanical, electrical)

The config generator is the FIRST thing users see. If it doesn't demonstrate these principles, the standard fails at its entry point.

---

## What It Is

The `architecture-model init` command is the **zero-config entry point** for the architecture-model-standard. It scans a project's directory structure and automatically generates a `.architecture-model.yaml` config file — the input contract that drives everything downstream (manifest generation, validation, slicing, context formatting).

"Self-bootstrapping" means: point it at any Python project, get a working architecture config with no manual setup.

---

## Module Architecture

| Module | File | Role |
|--------|------|------|
| CLI handler | `cli/main.py` (`_cmd_init`) | Entry point — resolves path, calls discovery, writes output |
| Config schema | `config/schema.py` | Dataclass definitions for all config types |
| Config loader | `config/loader.py` | Discovery logic — layout detection, F-block/layer/metric heuristics |
| Config writer | `config/loader.py` (`write_config`) | Serializes config to YAML |

## Data Flow

```
CLI: architecture-model init <path>
  │
  ├── Resolve path, check for existing .architecture-model.yaml (abort unless --force)
  │
  ├── discover_config(root)
  │   ├── name = root.name (directory basename)
  │   │
  │   ├── _discover_layers(root)
  │   │   └── Scan for well-known web/service/data/pipeline dirs
  │   │
  │   ├── _discover_metrics(root)
  │   │   └── Scan for countable artifact dirs (routers, models, migrations, templates)
  │   │
  │   ├── _discover_functional_blocks(root)
  │   │   ├── _find_source_root(root)        → detect src/flat/lib layout
  │   │   ├── _get_code_subdirectories()     → list subpackages with .py files
  │   │   ├── For each subdir:
  │   │   │   ├── Create FunctionalBlockConfig (F1, F2, ...)
  │   │   │   ├── rglob("*.py") for file list
  │   │   │   ├── _get_package_description() from __init__.py docstring
  │   │   │   └── _discover_sub_blocks() recursively (max 3 levels)
  │   │   └── Fallback: _fblocks_from_top_level_dirs() if no package structure
  │   │
  │   └── If no layers found but F-blocks exist → _derive_layers_from_blocks()
  │
  ├── Print summary to stdout
  │
  └── write_config(config, root)
      ├── config.to_dict() → nested dict
      ├── Add header comment ("Auto-generated by: architecture-model init")
      └── yaml.dump() → .architecture-model.yaml
```

## Layout Detection

`_find_source_root(root)` determines where the actual code lives. Checked in priority order:

| Priority | Layout | Detection Logic |
|----------|--------|-----------------|
| 1 | **src-layout** | `src/<child>/__init__.py` exists and `<child>` has code subdirectories |
| 2 | **flat-layout** | First sorted top-level dir with `__init__.py` AND code subdirectories |
| 3 | **lib-layout** | Same as src-layout but under `lib/` instead of `src/` |
| 4 | **Fallback** | No source root found → treat every top-level dir with `.py` files as an F-block |

**Excluded directories** (skipped during flat-layout scan): `tests`, `docs`, `scripts`, `build`, `dist`, `.git`, `.venv`, `venv`, `node_modules`, `__pycache__`, `.eggs`, `.tox`, `htmlcov`, `.mypy_cache`

## Layer Discovery

Hardcoded heuristic table (`_LAYER_HEURISTICS`). First matching directory per layer wins:

| Layer ID | Candidate Directories |
|----------|----------------------|
| `web-layer` | `app/routers`, `app/views`, `app/api`, `src/api`, `api/` |
| `services-layer` | `app/services`, `src/services`, `services/` |
| `data-layer` | `app/models`, `src/models`, `models/`, `alembic` |
| `pipeline-layer` | `scripts`, `pipeline`, `src/pipeline`, `jobs/` |
| `scheduling-layer` | `app/tasks`, `tasks/`, `celery/` |

**Fallback:** If no heuristic matches but F-blocks exist, `_derive_layers_from_blocks()` creates one layer per F-block directory with id `<dirname>-layer`.

---

## Metric Discovery

Searches for known countable artifact directories. First match per label wins:

| Label | Candidate Paths | Pattern | Excludes |
|-------|----------------|---------|----------|
| `router` | `app/routers`, `app/api`, `src/api` | `*.py` | `__init__.py` |
| `model` | `app/models`, `src/models` | `*.py` | `__init__.py`, `base.py` |
| `migration` | `alembic/versions`, `migrations` | `*.py` | (none) |
| `template` | `app/templates`, `templates` | `**/*.html` | (none), recursive |

## Functional Block Discovery

Each subpackage of the source root becomes an F-block:

1. `_find_source_root()` determines the code root
2. `_get_code_subdirectories()` lists immediate subdirectories that contain `.py` files
   - Skips `_`-prefixed directories and `__pycache__`
3. Each subdirectory becomes `F1`, `F2`, ... (numbered sequentially)
4. Block name: title-cased from directory name (e.g., `manifest` → `Manifest`)
5. Block description: from `__init__.py` docstring (first sentence), or fallback text
6. Block files: all `.py` files found via `rglob("*.py")`, excluding `__init__.py`

### Sub-block Recursion (max 3 levels)

`_discover_sub_blocks()` recurses into each F-block directory:

| Depth | ID Pattern | Example |
|-------|-----------|---------|
| 0 | `F1.A`, `F1.B` | Letter suffix |
| 1 | `F1.A.1`, `F1.A.2` | Numeric suffix |
| 2 | `F1.A.1.a`, `F1.A.1.b` | Letter suffix again |

- Only creates a sub-block if the directory contains `.py` files
- Names come from `__init__.py` docstrings (AST-parsed) or title-cased directory names
- Skips `.`-prefixed dirs and `__pycache__`

### Fallback: No Package Structure

If `_find_source_root()` returns `None`, `_fblocks_from_top_level_dirs()` treats every top-level directory with `.py` files as an F-block (same exclusion set plus `alembic`).

## Self-Bootstrapping: The Zero-Config Flow

"Self-bootstrapping" means the pipeline works on **any Python project with zero prior configuration**:

1. User runs `architecture-model init /path/to/project`
2. `_find_source_root()` detects the package layout (src/flat/lib)
3. Each subpackage becomes an F-block (`F1`, `F2`, ...)
4. `.py` files are enumerated, `__init__.py` docstrings provide descriptions
5. Sub-blocks are discovered recursively (max depth 3)
6. Layer/metric heuristics scan for known directory patterns
7. A complete `.architecture-model.yaml` is written
8. Subsequent `architecture-model manifest` reads this YAML and AST-scans accordingly
9. The LLM pipeline can then use `format_model_context()` to compress the architecture

Even without running `init`, the `get_config()` function (used by `generate_manifest`) auto-discovers on-the-fly if no YAML exists — so the manifest generator works without any prior `init` call.

## Config Schema (Full)

```
ProjectConfig
├── name: str                              # Project name (defaults to dir basename)
├── system: str                            # System name (defaults to dir basename)
├── output: OutputConfig
│   ├── model: str                         # "output/{project}/architecture-model.yaml"
│   ├── manifest: str                      # "output/{project}/reality-manifest.json"
│   └── artifacts: str                     # "output/{project}/artifacts/stage2"
├── layers: list[LayerConfig]
│   ├── id: str                            # e.g. "web-layer"
│   ├── dirs: list[str]                    # e.g. ["app/routers"]
│   └── description: str
├── functional_blocks: list[FunctionalBlockConfig]
│   ├── id: str                            # "F1", "F2", ...
│   ├── name: str                          # Title-cased from dir name
│   ├── dirs: list[str]                    # Relative dir paths
│   ├── files: list[str]                   # All .py files (excluding __init__.py)
│   ├── description_source: str            # From __init__.py docstring or fallback
│   └── sub_blocks: list[SubBlockConfig]   # Recursive (max 3 levels)
│       ├── id: str                        # "F1.A", "F1.B", "F1.A.1", etc.
│       ├── name: str                      # From docstring or title-cased dir name
│       ├── files: list[str]
│       ├── dirs: list[str]
│       ├── description: str
│       └── sub_blocks: list[SubBlockConfig]
├── metrics: list[MetricConfig]
│   ├── label: str                         # "router", "model", "migration", "template"
│   ├── path: str                          # Directory to count in
│   ├── pattern: str                       # Glob pattern (default "*.py")
│   ├── exclude: list[str]                 # Files to exclude
│   └── recursive: bool                    # Whether to use ** glob
└── root: Path                             # Runtime-only, not serialized
```

**Derived properties** on `ProjectConfig`:
- `layer_dir_map` — `{layer_id: [dirs]}` for merger
- `fblock_dir_map` — `{dir_or_file_prefix: block_id}` for merger heuristics
- `fblock_dict` — legacy dict format `{block_id: {name, dirs, files, description_source}}`
- `metrics_paths` — `{label: resolved_Path}`
- `resolved_output()` — returns `ResolvedOutputConfig` with absolute paths

## Interface with CAP-F2 (Manifest Generation)

The config YAML is the **input contract** for the manifest generator:

```
init → .architecture-model.yaml → generate_manifest() → reality-manifest.json → validator/extractor
```

`generate_manifest(project_root, config=None)` in `manifest/generator.py`:
- If no config passed, calls `get_config(root)` which loads `.architecture-model.yaml` if it exists, otherwise runs `discover_config()` (same auto-discovery as `init`)
- Uses `config.fblock_dict` to iterate F-block definitions
- Passes `block_cfg.sub_blocks` to the block processor for hierarchical scanning
- Uses `config.layers` to scan additional directories beyond F-blocks
- Uses `config.metrics` for `_compute_metrics()`

The config defines **what to scan and how to group it**. The manifest generator does the actual AST scanning within those boundaries.

## Limitations

1. **Python-only** — all heuristics assume Python projects. Layer heuristics target Python web frameworks (FastAPI/Django patterns). No support for JS/Go/Rust/Java projects.

2. **Web-framework bias** — layer heuristics only match `app/routers`, `app/models`, `alembic`, etc. CLI tools, data science projects, and libraries without these dirs get no layers from heuristics (falls back to one-layer-per-fblock).

3. **Single source root** — `_find_source_root()` returns the first matching package. Monorepos with multiple packages under `src/` only get the first one discovered.

4. **Flat-layout first-match fragility** — for flat layout, takes the first sorted directory with `__init__.py` and code subdirs. If a project has multiple top-level packages (e.g., `mylib/` and `utils/`), only the alphabetically-first one with subdirs becomes the source root.

5. **Root-level `.py` files silently dropped** — files directly in the source root (not in subdirs) are not captured in any F-block. A comment in the code references a "Core" block but it's not implemented.

6. **`_`-prefixed dirs excluded** — `_get_code_subdirectories()` skips any subdirectory starting with `_` (like `_internal`, `_utils`), potentially missing significant code packages.

7. **Sub-block `files` always empty** — `_discover_sub_blocks()` creates sub-blocks with `files=[]` — only directories are recorded, not the individual files within sub-blocks.

8. **Metric heuristics are static** — only 4 hardcoded metric types (router, model, migration, template). No way to auto-discover project-specific countable artifacts.

9. **No `pyproject.toml` / `setup.cfg` awareness** — layout detection doesn't consult packaging metadata to determine the actual package name or source root. Relies purely on filesystem heuristics, which can disagree with the declared package structure.
